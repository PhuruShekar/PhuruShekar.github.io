How the Music tab gets its data

Once a day a GitHub Action asks Last.fm for my top five tracks and writes them to music.json. The site reads that file. “Last played” is the only part fetched live, straight from Last.fm, when someone opens the tab.

For me only. This page lives in docs/, which _config.yml keeps off phurushekar.com, and nothing links to it.

The daily run, step by step

  1. 09:17 UTC. GitHub starts .github/workflows/music.yml. Scheduled workflows only run from the repository’s default branch, which is gh-pages, so the file has to be pushed there. The odd minute avoids the top of the hour, when GitHub’s queue is busiest; a run can still start a few minutes late.
  2. Checkout. It checks out only .github/scripts, the one folder it needs.
  3. Pull from Last.fm. node .github/scripts/music.mjs makes two calls with the key from the LASTFM_API_KEY secret:
    • user.getrecenttracks, limit 1: what I played last, or what’s playing right now.
    • user.gettoptracks, period 1month, limit 5. Last.fm’s “1month” means the last 30 days, not the calendar month, so the tab says “last 30 days”.
    It writes the answer to music.json. If either call fails, the script throws, the run goes red, nothing is pushed, and GitHub emails me.
  4. Publish. A fresh git repository is made around that one file, committed as github-actions[bot] and force-pushed to the data branch. The branch only ever holds one commit, so it never grows.
  5. Read. When the Music tab opens, script.js fetches https://raw.githubusercontent.com/PhuruShekar/PhuruShekar.github.io/data/music.json. GitHub caches raw files for about five minutes, so a new file can take that long to show up.

Why a separate data branch

I make changes on gh-pages and release with git push origin gh-pages:master. If the Action committed music.json to either branch every day, my local gh-pages would always be behind, and the release push would be refused until I pulled. A branch that only the Action writes to stays out of the way: my release flow is unchanged and the music updates without a release.

The cost is one cross-origin request to raw.githubusercontent.com, made only when someone opens the Music tab. The alternative was switching GitHub Pages to deploy from an Action, which would also have changed how every release goes out.

Two keys, and why one of them is public

The Action’s key: secret

Stored as the repository secret LASTFM_API_KEY (Settings → Secrets and variables → Actions). It never appears in the repository or in logs; GitHub masks it.

The page’s key: public on purpose

“Last played” has to be asked for from the visitor’s browser, so that key is in script.js (LASTFM_KEY) where anyone can read it. A Last.fm API key on its own can only read public data, such as my scrobbles. It can’t post, scrobble or change my account; that needs the separate shared secret, which neither path uses.

It’s a second key made just for the page, so if anyone abuses it I can delete it at last.fm/api/accounts without breaking the Action.

While LASTFM_KEY is empty, the page skips the live call and shows the last-played track from music.json instead, marked “from the daily update”.

What’s in music.json

{
  "user": "pshekr",
  "updated": "2026-10-21T09:17:42.000Z",   // when the Action ran; the page shows its age
  "period": "1month",                      // Last.fm's rolling 30 days
  "recent": {                              // fallback for "last played"
    "track": "…", "artist": "…", "url": "https://www.last.fm/music/…",
    "nowPlaying": false,
    "playedAt": "2026-10-21T08:55:00.000Z"
  },
  "top": [                                 // most played first, up to 5
    { "track": "…", "artist": "…", "url": "…", "plays": 42 }
  ]
}

One-time setup

  1. Make two API keys at last.fm/api/account/create, one called “phurushekar.com Action” and one “phurushekar.com page”. The callback URL can stay empty.
  2. Add the Action’s key as a repository secret named LASTFM_API_KEY.
  3. Paste the page’s key into const LASTFM_KEY = '' in script.js.
  4. Commit and push gh-pages (the workflow has to be on the default branch to be scheduled), then release with git push origin gh-pages:master.
  5. Actions tab → Music → Run workflow, to make the data branch now instead of tomorrow morning.
  6. Check it: open the raw URL above, then the Music tab on the site.

Running and checking it

  • Run now: Actions → Music → Run workflow. The log’s last line says how many tracks it found and what played last.
  • See the file: the raw URL above, or the data branch on GitHub.
  • Change the time: the cron line in music.yml is in UTC. 17 9 * * * is 2:17 a.m. in Seattle in summer, 1:17 a.m. in winter.
  • Change the user: LASTFM_USER in music.yml and LASTFM_USER in script.js.

Saying it out loud

“My site is static, with no server. For the music section, a scheduled GitHub Action runs once a day as a free cron job: it calls the Last.fm API with a key kept in GitHub Secrets, writes a small JSON file, and force-pushes it to a branch that only holds data. The page reads that file, so visitors never wait on Last.fm for the top tracks. The one live piece, the last song I played, is fetched from the browser only when someone opens the tab, and if Last.fm doesn’t answer, the page falls back to the daily copy and shows how old it is.”
